# FPGA retest: RESET ×64, INT and NMI

[Waveform gallery and raw samples](/Users/orl/Projects/electronics/zxx-pcb/rp2350b_driver/derived/event_retest_20261007/index.html)

Completed 89 hardware captures: 64 RESET attempts and all 25 interrupt/NMI scenarios from the previous test. CLK was 1 MHz; RP system clock 150 MHz; GPIO sampled every four system clocks (26.667 ns). The RP async driver was built from the current source without changes. Normal firmware was saved before testing, restored and verified afterward. OpenOCD was stopped. No FPGA programming or production source edits were performed.

**Results: RESET 57/64 passed, 7/64 failed. All 25 interrupt/NMI scenarios passed the recorded behavioral checks.** No recording had a sampler FIFO stall. Source/ELF snapshots and raw RTT, TSV and decoded JSON are retained alongside this report. This is a finite test of the currently connected board, not proof of all opcode, phase or speed combinations.

## RESET: 64 attempts

Eight scenarios were each repeated eight times. Each attempt began with an RP reset and normal initial CPU boot, followed by one captured CPU RESET stimulus. Thus these are 64 independently initialized attempts, not 64 consecutive CPU resets without reinitializing the RP. The 64 count excludes the startup resets needed to launch the test program.

A pass requires the complete initial sequence: FETCH 0000=C3; READ 0001=00; READ 0002=01; FETCH 0100=F3. All failures still addressed 0000 first, so address alone would falsely classify them as passes.

| Scenario | Assert CLK | Release CLK | Pass | Fail |
|---|---:|---:|---:|---:|
| reset_halt_high | 1 | 1 | 8/8 | 0/8 |
| reset_halt_low | 0 | 0 | 7/8 | 1/8 |
| reset_high_release_low | 1 | 0 | 6/8 | 2/8 |
| reset_low_release_high | 0 | 1 | 8/8 | 0/8 |
| reset_run_high | 1 | 1 | 8/8 | 0/8 |
| reset_run_low | 0 | 0 | 6/8 | 2/8 |
| reset_wait_high | 1 | 1 | 8/8 | 0/8 |
| reset_wait_low | 0 | 0 | 6/8 | 2/8 |

All 32 releases during CLK HIGH passed; 25/32 releases during CLK LOW passed. This is an observed phase association, not proof of root cause or an unbiased failure-rate estimate. Assertion and release phases were generated by PIO and checked in the actual samples. The reset hold lasted approximately 17–21 clocks; minimum-pulse-width behavior was not tested.

On successful restarts, first external fetch (`MREQ=RD=M1=0`) occurred 0.987–1.040 µs after LOW-phase release and 1.493–1.547 µs after HIGH-phase release. Those are approximately 1 and 1.5 CPU clocks, respectively.

The seven failures consumed stale data (`00` or `77`) instead of `C3` on the first fetch. WAIT was released before the expected opcode became available. The CPU then followed the wrong instruction stream. In the failed OUT/WAIT cases the stale value was 77, matching the previous OUT data. A later IRQ-marker write in those RESET traces is accidental code execution, not an actual interrupt: INT remained high.

This remains consistent with an old RP reply/DATA_READY state surviving a reset-aborted transaction, but these traces do not observe IRQ3 directly. The FPGA update did not eliminate the system-level RESET failure. The next diagnostic should record service completion/DATA_READY around RESET, then ensure an aborted pre-reset reply cannot release WAIT for the first post-reset request. This retest does not prove whether the remaining correction belongs solely in the RP driver or also in FPGA reset handling.

## Interrupts: 16 scenarios passed

The prior missing M1/IORQ overlap is gone. Enabled requests now produce one valid acknowledge, with the intended data delivered. No malformed acknowledge-like interval was found by the previous decoder.

- IM0 RST08 (CF): running and HALT cases push the correct return PC, fetch 0008, execute the handler and return.
- IM1: running and HALT cases fetch 0038, execute the handler and return with a valid acknowledge.
- IM2: acknowledge data is 10; table reads are 4010=30 and 4011=02; execution reaches 0230 and returns correctly.
- DI suppresses INT while running and while halted in all three modes. DI+HALT stays halted throughout the recorded interval.
- EI; INC B accepts INT only after the INC B instruction, saving PC 0110. EI; DI suppresses the interrupt.
- IM0 CALL: acknowledge CD, read operands 00 and 02 at 0112/0113, push return PC 0114, execute 0200 and return to 0114.
- IM0 JP: acknowledge C3, read operands 00 and 02 at 0112/0113, execute 0200 **without a stack push**.

The shared JP target contains RETI for the CALL/RST tests. Because JP creates no return address, that RETI subsequently reads the initial stack and jumps to 0000; this is a test-program artifact, not a failed JP. The JP pass covers opcode/operand delivery, correct destination and absence of an unwanted push. It does not claim a valid return from JP.

These are tested instruction examples, not exhaustive IM0 coverage. The current Debug firmware inserts software-service WAIT extensions, so latency is not a bare-CPU cycle specification.

## NMI: 9 scenarios passed

NMI works with DI and EI, running and from HALT. The handler at 0066 writes 5A and executes RETN. Holding NMI low causes one entry; two falling edges cause two entries. After RETN, INT is accepted when interrupts were enabled before NMI, and ignored when they were disabled. In the near-coincident NMI/INT test, NMI is serviced first and INT afterward. This uses two adjacent GPIO writes, not an exhaustive timing-order sweep.

## Artifacts and reproduction

`reset_results.tsv` and `reset_results.json` enumerate all 64 reset captures. `interrupt_results.json` contains individual behavioral assertions. Each capture has the raw RTT log, per-sample TSV and decoded bus-cycle JSON. The gallery includes images for all 25 interrupt/NMI scenarios and eight representative RESET scenarios (including a failure). Other RESET captures can be rendered with the same analyzer.

Eight invocations of `tests/run_event_tests.py` used `--cases 0,1,2,3,4,5,31,32`, separate output directories, and the same ELF; only the first invocation flashed. A final invocation used `--cases 6:31 --no-flash`. `tests/build_event_tests.py` built in `/tmp/z80_event_retest`. Sources, test ELF and hashes are archived here. `restore_console.txt` records successful restoration verification.

The tests deliberately leave the production PIO unchanged. They do not validate arbitrary asynchronous reset offsets, minimum RESET width, analog signal quality, all interrupt vectors/opcodes, or operation above 1 MHz.
