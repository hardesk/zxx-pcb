# Bus request speed and frame stability — 2026-10-08

## Result

Raising the RP2350 system clock from 150 to 300 MHz (variant **B**) moves the
RZ80 from about two WAIT states per transfer to one. At an unchanged 5 MHz CLK
and with the LCD active:

- Measured **76,664 T per 20 ms frame**, against 63,662 before (+20.4%).
- Frame-to-frame σ is 9 T; the range over 200 frames was 76,660–76,683.
- Every workload now delivers 3.66–4.06 MHz effective, which is 73.3k–81.2k
  T per frame and above Pentagon's 71,680.
- VIBRATE, which previously corrupted its drawing table within seconds at
  50 Hz, ran 45 s at 50 Hz with intact entry code and IM2 vector and zero
  invalid table entries.

C++ hot-path trimming alone (variants **A/A2**, 150 MHz) gained about 2%. A
200 ns quantization step explains the difference; see the latency model below.

After review, 300 MHz is the **build default** (`RP_SYS_CLOCK_KHZ=300000`
in Makefile/CMake); `RP_SYS_CLOCK_KHZ=150000` restores stock speed with the
A2 code. The board was left running the verified B ELF
(`derived/bus_speed_20261008/build_B`, SHA-256 f0ad7dc6…). The default
`derived/drv_rel` build has the same code, but its link layout differs. Run
`make flash` before using `make test-bus-benchmarks` with the default ELF.

## Latency model (from the TV80 source)

`tv80s.v` registers MREQ/RD on the rising CLK edge that starts T2. It samples
`wait_n` and latches data on the following rising edges (`tstate[2] && wait_n`).
The WAIT guard asserts WAIT on MREQ, so the number of wait states is:

```text
waits = ceil((MREQ-to-reply latency - 200 ns) / 200 ns)   at 5 MHz CLK
```

The production median of 453 ns (`bus_latency_20261008.md`) gives 2 waits.
frame_work measured 2.19 waits per transfer. A reply under about 400 ns gives
1 wait; under 200 ns would give 0, which a CPU in the loop cannot reach.
The path is a fixed count of RP cycles: detector, CPU poll and lookup,
service data/OE setup, guard release. Doubling clk_sys therefore roughly
halves it, while shaving cycles at 150 MHz does not cross the 400 ns step.
The RZ80 instantiates TV80 with `T2Write=1` and `IOWait=1`, so memory writes
follow the same rule. I/O cycles add their automatic extra T state.

23% at 300 MHz (14–19% at 150 MHz); see `bus_benchmarks_20261008.md`.

## Candidate directions — measured verdicts

| Candidate from the brief | Verdict | Evidence |
| --- | --- | --- |
| Copy 128-0/128-1 ROMs from flash to SRAM | Not worth it | A full 16 KiB ROM sweep from XIP is 0.7% slower than the identical sweep in RAM (258.2k vs 260.3k ops/s). The XIP cache hides it. |
| Precompute `select_rom()` memcmp | Negligible | It runs only on 0x7FFD writes, not per transfer. Could still be cached for tidiness. |
| Move housekeeping (RTT/keyboard/tape/button) | Low value | Without host traffic σ is 9–13 T. With ~45 status requests/s the worst frame lost 0.6%. Uploads are bounded per poll. |
| Pure PIO/DMA service for RAM/ROM | Not needed now | B already reaches the 1-wait floor. Only 0 waits would improve on it, which needs a reply within ~200 ns of MREQ, including paging lookup. |
| INT tied to delivered T-states | Deferred | On B the slowest workload still gets 73.3k T per 20 ms. A pin-based count would need the T2/Tw sampling edge decoded exactly; the existing LCD counter's large, unexplained bias shows that is not yet solved. A "≥20 ms AND ≥71,680 T" gate remains a robustness option. |
| Shorter PIO handshakes | Indirectly done | 300 MHz halves every PIO and CPU stage. The service SM's `[4]` setup delay was left in cycles, so data-to-WAIT is ~33 ns instead of ~67 ns. All data checks and VIBRATE passed. |
| C++ hot-path trims (A/A2) | Kept, minor | Fast read/write inline, IO/tape handlers moved to SRAM, reset handling off the hot path. Worth +2% at 150 MHz. |

## Changes in the tree

- `main.cpp`:
  - `run_z80_bus` handles MREQ+RD (no tape observer) and 128K RAM writes
    inline, about 11 instructions from RX read to TX write (was ~19). Before,
    the TX pointer was reloaded from the stack and the reset flag was tested
    twice per transfer.
  - Other requests go to `service_pio_request`, now outlined in SRAM.
    `handle_io_in/out` and `service_tape_read` also moved from flash to SRAM.
  - A requested reset completes in `reset_on_next_request()` with the same
    transaction-safe order as before.
  - `configure_system_clock()`: when `RP_SYS_CLOCK_KHZ` ≠ 150000, it sets
    VREG to 1.20 V, scales QMI flash timing to keep a 50 MHz SCK (clkdiv
    3→6, rxdelay 2→4, written from SRAM), then calls `set_sys_clock_khz`.
    The boot banner prints the RP clock.
- `CMakeLists.txt`/`Makefile`: `RP_SYS_CLOCK_KHZ` option (default 300000); links `hardware_vreg`.
- `z80_frame_interrupt.cpp`: above 255 MHz it uses 0.5 µs PWM ticks (divider
  150, wrap 39999), keeping a 20 ms period and 7 µs pulse. The old code hit a
  hard assert at 300 MHz.
- LCD (`zxdisplay.cpp`), CLK and T-state counter dividers already derive
  from clk_sys. At 300 MHz the LCD measured 50.5 frames/s, frame work
  19.2 ms (unchanged).
- `tests/run_bus_benchmarks.py`:
  - Adds `--extended` with `rom_read`, `rom_ram_read` and `frame_work`.
  - Sweeps use carry-chained `ADC A,(HL)`, checked against a host model, so
    any single misread byte in 1M reads fails the run.
  - Each case starts from the cloned boot ROM and the original C000 mapping.
  - Accepts 0.5 µs PWM ticks.
- `tests/test_rom.py` stubs the SDK section macro.
- `tests/test_frame_interrupt.py` covers 300 MHz.

Host regressions: ROM/banking, tape pulse, tape fast-load, keyboard, frame
interrupt, and the async PIO model (`make test-async-pio`) all pass.

## Limits and open items

- The older wait-sequence checker (`build_async_speed.py`) patches a main.cpp
  structure that no longer exists (CP/M boot, `bus.read_request()`), so it
  was not run. 300 MHz qualification rests on the byte-verified sweeps, RAM
  write verification, I/O results, about 6M benchmark transfers and 45 s of
  VIBRATE. Porting that checker and a longer soak (minutes of demos, tape
  uploads) are still recommended for the new default.
- 1.20 V / 300 MHz is a common RP2350 operating point, but outside the
  datasheet's nominal 150 MHz. Thermal behaviour was not measured.
- POWER_UP's notes ask for 71,680 T per INT with no waits. B gives ~76.7k T
  for typical code, but contended/raster-exact effects are not emulated.
