# RESET, INT and NMI hardware tests — 2026-10-07

[All 33 signal diagrams and text captures](/Users/orl/Projects/electronics/zxx-pcb/rp2350b_driver/derived/event_tests_20261007/index.html)

Tested the connected TANG/RP2350 board at 1 MHz with the current async PIO source unchanged. There were 33 distinct cases plus eight repeated RESET cases. The saved normal RP firmware was restored, flash verification passed, and the test OpenOCD server was stopped. No FPGA source or bitstream was changed.

## Findings

- **RESET is not fully reliable:** 15/16 captures restarted with `JP 0100`; one fetched stale `00` at address `0000` and followed the wrong instruction stream. This is an observed count, not an estimate of failure probability.
- **IM1 reaches its handler and returns, but interrupt acknowledgement is malformed.** `/M1` and `/IORQ` never overlap low in the captured acknowledge-like interval. The driver consequently delivers zero interrupt opcodes/vectors.
- **IM0 and IM2 fail end to end.** IM0 does not receive the intended RST/CALL/JP, and IM2 reads the wrong vector table entries.
- **NMI passes the tested scenarios:** DI/EI, running/HALT, held-low, repeated edges, RETN interrupt-state restoration, and NMI-before-INT ordering.

## Measurement and limitations

GPIO0–31 and GPIO16–47 were recorded by paired PIO/DMA samplers every four 150 MHz system clocks: 26.667 ns/sample. ADDR is GPIO23:8 and DATA is GPIO7:0. All 41 recordings have zero sampler FIFO stalls. Shared-pin disagreements at transitions indicate a small cross-recorder sampling uncertainty; allow about one sample for cross-bank edge comparisons. CLK, RESET, WAIT, M1, IORQ, MREQ, RD and WR are all in the same low-bank recording.

RESET phase was generated by a spare hardware PIO state machine; the recorded clock level confirms assertion and release phase. Firmware serviced requests without printing during capture. Nevertheless this is a Debug build with software bus service, so WAIT stretches cycles substantially. NMI/INT latency below includes those waits and instruction completion. It must not be read as an un-stalled CPU timing specification. This is digital observation at the RP inputs, not a measurement of analog voltage, signal integrity, or internal FPGA registers.

The reference behavior is Zilog's documented RESET, interrupt modes, EI delay, NMI and RETN behavior. IM0 may execute a multi-byte instruction: its initial opcode arrives during interrupt acknowledgement and later bytes are ordinary memory reads. See the [Z80 CPU User Manual](https://www.zilog.com/docs/z80/um0080.pdf), interrupt overview and IM 0 instruction description.

Initial captures with a test-harness pulse-duration/phase problem were excluded and retained separately as pilots. Only the top-level case logs and `reset_repeat` are used here.

## RESET

Each pulse was roughly 17–21 CPU clocks long. These tests do not establish the minimum reset pulse width. The first external instruction fetch is defined as `/MREQ` and `/RD` both low with `/M1` low; a falling M1 alone starts earlier. All captures first addressed `0000`, but address alone was insufficient to prove a successful restart.

The six initial running/HALT/pending-WAIT cases all restarted correctly. Normal first-fetch timing was about 1.0 clock after release during CLK LOW, or 1.5 clocks after release during CLK HIGH, with one rising CLK edge between release and the fetch. M1 began about 0.5 or 1.0 clock after release, respectively. The opposite-phase cases and repeats are included below.

In the failed LOW-assert/HIGH-release capture, the first fetch began only 0.533 µs after release. `/WAIT` pulsed briefly and released while DATA was still `00`. The host subsequently supplied `C3`, but after the first read had ended. The next external opcode fetch was at `0001`, instead of operand reads at `0001/0002` followed by a fetch at `0100`. The eventual write of A5 to the IRQ marker was accidental execution through the test image, **not an interrupt**: INT was high and interrupts were disabled.

A plausible driver mechanism is a late reply to a request aborted by RESET leaving DATA_READY/IRQ3 pending for the first post-reset request. The current guard/service do not flush their state on RESET; only the detector gates new scans. The waveform proves premature WAIT release and late opcode availability, but does not expose IRQ3 or prove this mechanism. The immediate eight-case repeat passed. RESET while WAIT is active was tested by deliberately withholding an OUT reply until the reset hold ended.

Bus control strobes were idle by the assertion sample or next sample in these traces. Some were already idle; this is not a bound on complete internal CPU reset latency.

### FPGA source consistent with the captures

The local RTL has three concrete problems to address before repeating IM0/IM2 qualification:

1. `z80_timing.v`, BUSOP_INTA, drives M1 low only for t≤2 and IORQ low only for t≥3. They cannot overlap.
2. `z80_core.v` latches INTA data at T2, before that IORQ window, and excludes INTA from `wait_capture_phase`. Correct the complete acknowledge handshake and latch data only after the responder's valid-data/WAIT sequence.
3. `EXEC_INT` implements IM0 as `tmp8 & 0x38` after an unconditional return-address push. General IM0 needs to execute the supplied opcode and fetch additional bytes, with stack effects belonging to that instruction. Fixing the acknowledge pins alone will not implement CALL/JP properly.

These are observations of the local RTL, not proof of the exact source revision programmed into the FPGA. The measured acknowledgement waveform is consistent with it. The multi-byte hardware tests currently fail before opcode delivery, so they cannot separately establish the CPU's multi-byte execution behavior.

## NMI

Each single-edge case fetched 0066, wrote 5A to 6001 and executed RETN. Return addresses were pushed to 8FFF/8FFE and read back. DI did not block NMI; HALT was exited. The HALT return addresses were 010F (DI) and 0111 (EI), the instructions following the respective HALTs.

Holding NMI low for approximately 90 µs caused one entry. Two falling edges caused two entries. After RETN, a subsequent INT reached the IM1 handler if interrupts had been enabled before NMI, and was ignored if they had been disabled. In the priority case NMI was asserted immediately before INT by two GPIO writes: NMI was serviced first and INT after RETN. This tests near-coincident requests, not every possible edge ordering. The INT portion retains the acknowledgement defect described above.

## Recommended changes and follow-up

- Fix FPGA INTA M1/IORQ overlap, WAIT sampling and data-latch timing together. Then rerun all IM modes with different supplied opcode/vector values.
- Implement general IM0 instruction injection before claiming multi-byte support; rerun RST, CALL and JP and check stack effects and return addresses.
- Make CPU RESET cancel or drain the RP transaction state coherently: detector/service FIFO contents, outstanding replies, DATA_READY and data output-enable. Keep WAIT high while idle, but prevent a pre-reset completion from releasing a post-reset request. Instrument IRQ3/service state to confirm the intermittent failure before choosing the implementation.
- Repeat RESET at many offsets within an outstanding read/write, not only clock HIGH/LOW, then test minimum pulse duration separately. These captures do not establish exhaustive reset reliability.

## Reproduction

The four new test files in `tests/` build an isolated firmware using the current driver, run numbered hardware cases through an existing OpenOCD server and render the capture logs. Production firmware source was not edited.

```sh
/opt/openocd-master/bin/openocd -f interface/cmsis-dap.cfg -f target/rp2350.cfg -f rtt.cfg
# In another terminal, from rp2350b_driver:
python3 tests/build_event_tests.py /tmp/z80_event_tests
python3 tests/run_event_tests.py /tmp/z80_event_tests/build/event_tests.elf derived/event_tests_NEW --cases 0:33
/opt/homebrew/bin/python3.11 tests/analyze_event_tests.py derived/event_tests_NEW
```

The runner flashes firmware. Save the firmware you intend to restore before rerunning. `sources/` contains the tested driver and harness copies, source hashes and tooling; `event_tests.elf` is the final isolated test image. The original 31-case run preceded the addition of two cross-phase cases; those additions do not alter cases 0–30. `restore_console.txt` records successful restoration verification. Raw TSV files are independently inspectable by sample index and time. Pilot folders are excluded from the results.
